# 不涉及摄像头的性能工作负载

现有 `bench` 命令测量确定性的 1x4 ReLU 图，适合确认设备启动、基础 MYRIAD 执行路径和计时稳定性，不能代表应用吞吐。SDK 现在提供任务级和 worker 推理计时，可用于区分 worker/模型启动成本与热态推理。

## 值得测量的问题

| 实验 | 要回答的问题 | 工作负载 |
| --- | --- | --- |
| 冷启动与热态复用 | 启动 worker、编译 IR 与连续推理各占多少时间？ | 先提交一个任务，再对同一注册模型连续提交任务；比较 `worker_start_count`、`last_task_milliseconds` 和 `last_inference_milliseconds`。 |
| 模型切换成本 | 应用交替使用模型时，驻留单模型是否值得？ | 比较按模型分组的长批次与严格交替提交，统计 worker 启动和切换次数。 |
| 主机/worker 传输开销 | JSON 编码、管道传输、校验和结果解码相对设备调用增加多少端到端耗时？ | 使用真实静态 IR 扫描输入/输出元素数，比较 SDK 任务时间和 worker 推理时间。两者差值代表合并后的 wrapper/runtime 开销，不是纯 USB 延迟。 |
| 张量大小扩展 | 传输和序列化从何时开始主导计算耗时？ | 使用受支持的静态 f32 信号处理或表格模型，逐步增加张量规模，最高不超过协议限制。固定计算图和输入值，只改变规模。 |
| 队列延迟和背压 | 当生产速度超过单个 NCS2 的执行速度时，应用会怎样？ | 按固定速率提交；记录队列深度、queue-full 次数、等待时间、完成延迟和结果保留内存。 |
| 持续运行与恢复 | 长时间运行是否出现延迟漂移？受控故障后 worker 多久恢复？ | 重复固定工作负载，记录单调时钟时间戳、逐任务延迟、worker 重启和 USB 重连情况。 |
| USB 拓扑和供电 | 直连端口、有源 hub、USB 2/3 路径会否影响稳定性或延迟？ | 每种拓扑运行同一模型和输入序列，记录协商链路、hub、供电、环境条件和设备信息；发布结果时隐藏序列号。 |

## 无摄像头应用负载

- **音频关键词识别：** 输入音频文件预先计算好的 MFCC 或 log-mel 窗口，将 NCS2 推理与麦克风采集、特征计算分开测量。
- **传感器异常评分：** 对振动、温度或设备遥测窗口运行小型静态模型，输出异常分数或类别向量。
- **表格分类：** 使用固定特征向量评估本地分类、质量检查等工作负载。
- **文本分类：** 尝试小型静态分类器处理 token 或 embedding 向量。先通过 `inspect` 和 MYRIAD 实际编译检查算子与张量限制，再测性能。
- **信号变换：** 对音频或传感器块测试小型去噪、回归模型，并单独记录主机预处理时间。

这些是候选工作负载，不代表导入的特定模型必然可编译。每次测量都应固定 IR/BIN、输入和独立输出参考，执行预热，并收集足够样本报告 p50/p95 及 min/mean/max。首次模型编译时间应与热态推理分开。每份结果都记录模型哈希、worker 协议、OpenVINO revision、主机、USB 拓扑和供电方式。

## SDK 计时口径

`last_task_milliseconds` 统计该任务启动或切换 worker、读取/编译模型、请求传输和校验的耗时，不包含 SDK 队列等待。`last_inference_milliseconds` 由原生 worker 从 `start_async()` 计时到 `wait_for()` 完成，不包含 JSON 编码和输出序列化。schema 1 与 schema 2 均提供此计时。

两个计时值的差包含多个主机侧阶段，不能直接称为 USB 延迟。受控传输实验还需分别记录输入序列化、管道读写、worker 张量复制和输出序列化时间。这些测量应放在独立实验工具中，不进入默认应用 SDK。
